# 工单：处理、排查、发布、回滚与实测（handoff_ticket.md 第 3 轮）

本文是工单系统的运维说明，面向处理工单的管理员和负责部署的人。功能设计见根目录 `handoff_ticket.md`，后端命令见 [backend/DEPLOYMENT.md](../backend/DEPLOYMENT.md)。

## 结论边界（先读）

- 下文的“开发方证据”都在本机或 CI 的私有 PostgreSQL、本地 Next.js 和 Chromium 上取得，**不是**生产环境的结论。生产环境是否正常，以你部署后按第六节逐条实测的结果为准，结果请填在第六节的表里或 `handoff_ticket.md` 第 18 节。
- 工单没有附件、邮件或短信通知；用户只能在网站上看到回复（侧边栏未读角标），管理员只能在管理后台看到新工单（标签角标，每 15 秒刷新）。
- **到期删除不可恢复。**每张工单从提交时起保留 30 天，到点后两端立即看不到，维护循环随后物理删除工单和全部对话。没有回收站、没有导出、数据库备份之外没有任何副本。需要留存的内容请在到期前自行复制。

## 一、管理员如何处理工单

入口：管理后台 → “工单”标签（`/admin/console/tickets`）。标签上的数字是**待处理**（等客服回复）的工单数；有待处理工单时，左侧栏“管理后台”旁有一个小圆点。页面不用刷新：列表和角标每 15 秒更新一次，新进入当前页的工单会浅色高亮 5 秒。

1. **看队列。**默认筛选“待处理”，等待最久的排在最前，“等待时长”列显示已经等了多久。也可以按“已回复”“已关闭”“全部”、分类、关键词（工单号前缀、用户邮箱、标题）筛选，筛选条件保存在网址里，可以直接分享给另一位管理员。
2. **打开详情。**点一行打开右侧详情（网址带 `?ticket=`）。能看到工单号、分类、设备、关联订单（点击跳到“订单与支付”并打开该订单）、提交人（点击跳到“用户管理”并打开该用户，含账号状态、当前套餐和到期时间）、创建时间、删除日期和全部对话；客服消息标注是哪位管理员发出的（只有管理员能看到，用户侧一律显示“客服”）。详情每 10 秒刷新，**刷新不会清空正在输入的回复**；用户发来新消息时，对话底部提示“用户有新消息”。
3. **回复。**写好后点“发送回复”，状态变为“已回复”，用户侧边栏出现未读角标。双击只会发送一次。正文最多 3000 字，纯文本：HTML、Markdown 和链接都按原文显示，不会变成可点击的链接。
4. **关闭。**点“关闭工单”，可以选填一句关闭说明（最多 500 字，作为最后一条客服消息出现），也可以不填直接关闭（用户看到“客服已关闭此工单”）。关闭是终态，双方都不能再回复；用户有新问题需要另开一张。
5. **“用户有新回复，请先查看”。**关闭时如果用户刚好发来新消息，关闭会被拦下，详情自动刷新。看完新消息再决定回复还是关闭。
6. **账号注销中。**提交人正在注销时详情显示“账号注销中”，不能回复（用户已无法登录），仍然可以关闭。账号清除后，他的全部工单一起删除。
7. **代用户查看。**需要从用户角度确认时，用现有的“模拟登录”打开 `/tickets`：只读，看不到提交、回复、关闭按钮，也不会把客服回复标记为已读。

用户侧的约束（回答用户提问时用得上）：同时最多 3 张未关闭的工单；每天最多提交 5 张（按 UTC 自然日）；每小时最多回复 30 条（按整点小时）；每张工单最多 100 条消息，满了只能关闭或另开。超出时用户看到“操作太频繁，请于 X 分钟后再试”或对应说明。

## 二、排查指引

先运行 `./doctor`（`cd backend && go run ./cmd/doctor` 或部署包里的 `bin/doctor`），看 `tickets` 段：

| 字段 | 含义 |
| --- | --- |
| `enabled` | `TICKETS_ENABLED` 的当前值 |
| `open` / `answered` | 未到期的待处理 / 已回复工单数 |
| `oldest_wait_seconds` | 最早一张待处理工单已经等了多少秒 |
| `expired_not_deleted` | 已过保留期**超过 1 小时**仍未被物理删除的工单数 |

`tickets` 段和整份 doctor 输出只有开关、数量和时长，没有工单号、标题、正文、邮箱或任何 ID。对应的警告：

| 警告 | 原因与处理 |
| --- | --- |
| `tickets_waiting_over_24h` | 有工单等了超过 24 小时没人回复。打开“工单”标签，默认排序的第一行就是它 |
| `tickets_expiry_lagging` | 有工单过期超过 1 小时还没删除，说明维护循环可能没有运行。读接口已经把它们隐藏，用户和管理员都看不到，所以这**不是**数据泄露，但要查清原因：API 进程是否在运行、日志里是否有 `maintenance: ticket expiry failed (will retry)`、数据库是否可写。清理在每个 API 进程启动时立即执行一次，之后每 10 分钟一次（多实例时用 advisory lock 保证同一时间只有一个实例在删），重启后端会立即触发一次 |

常见现象：

| 现象 | 原因与处理 |
| --- | --- |
| 用户说侧边栏没有“我的工单” | 管理员账号本来就没有这个入口（管理员看“管理后台”里的“工单”标签）；或 `TICKETS_ENABLED=false`；或 `/api/v1/meta` 里没有 `tickets_enabled`（后端比前端旧，见第四节的发布顺序） |
| 用户说“工单暂停受理” | `TICKETS_ENABLED=false`：用户仍能查看已有工单，但不能提交、回复或自行关闭；管理员照常回复和关闭，到期删除照常运行 |
| 用户说“工单服务暂未开放” | 前端是新版本，后端是工单之前的版本（`/meta` 没有 `tickets_enabled`）。升级后端 |
| 管理后台“工单”页显示“当前版本暂不支持工单” | 同上，后端早于工单功能 |
| 管理员看不到用户说的那张工单 | 先确认工单号；已超过 30 天的工单已被删除，无法恢复。“待处理”筛选不含已回复和已关闭的，换成“全部”再按工单号搜索 |
| 用户说提交时提示“处理中的工单最多 3 张” | 让用户关闭已经解决的工单，或由管理员关闭 |
| 回复后用户迟迟看不到角标 | 用户侧角标每 60 秒刷新，切换页面或回到页面时立即刷新；浏览器标签在后台时暂停。让用户切换一次页面 |
| 日志里有 `maintenance: ticket expiry changed N rows` | 正常：本轮删除了 N 张到期工单。日志只有数量，不含工单号或用户 |

**隐私约定**：工单正文从不写入日志、审计或 doctor。审计（`admin_audits`）只记录 `admin.ticket_reply`（工单 id 和正文长度）和 `admin.ticket_close`（是否带说明和说明长度）。排查时不要把工单正文贴进日志、截图群或外部工具；工单里可能有邮箱、订单号等个人信息。

## 三、配置

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `TICKETS_ENABLED` | `true` | 总开关。只接受布尔值。关闭时 `/meta` 返回 `tickets_enabled: false`，用户侧入口隐藏，提交、回复、用户关闭返回 403 `tickets_disabled`；已有工单只读可见，管理员照常处理，到期删除照常运行 |

保留期（30 天）和各项上限都是代码常量，没有环境变量。工单的限流计数存放在 `auth_rate_buckets` 表，过期行由邮件模块的每小时清理删除；未配置 SMTP 的环境里这些行会留存，体量极小，可以忽略。

## 四、发布顺序

1. 备份数据库，部署**后端**并迁移（只增不删，可重复执行）：`cd backend && ./api -migrate`。迁移新增 `tickets` 和 `ticket_messages` 两张表，不修改任何已有表，不会阻塞已有表的写入。
2. 运行 `./doctor`：`missing_tables` 为空，`tickets` 段 `enabled: true`、计数为 0；确认 `curl https://<站点>/api/v1/meta` 里出现 `"tickets_enabled": true`。
3. **再部署前端**。新前端只有在 `/meta` 声明 `tickets_enabled` 时才会显示入口和请求工单接口，所以先后端、后前端；反过来也不会报错，只是入口暂时不出现。
4. Nginx 或其他反向代理如果单独限制请求体大小，`/api/v1/me/tickets` 和 `/api/v1/admin/console/tickets` 需要至少 32 KB（3000 个汉字约 9 KB，加上 JSON 结构）。后端和 Next 代理本身都已按 32 KB 处理。
5. 按第六节做一次实测。

## 五、回滚

- 只想暂停受理，不需要回滚代码：`TICKETS_ENABLED=false` 并重启后端。前端入口随 `/meta` 自动隐藏，已有工单仍可查看和由管理员收尾。
- 回滚代码：可以只回滚前端，也可以连同后端一起回滚（先前端、后后端），不需要手动处理数据。回滚到工单之前的版本（PR #95，75f906d）时：
  - 新表留在数据库里，旧版本不读不写；旧版本没有工单路由（请求返回 404），旧前端也没有入口，工单只是暂时不可见，在线客服不受影响；
  - 旧版本清除注销账号时直接删除用户行，外键级联删除该用户的工单和对话，不会失败；
  - 旧版本不运行工单到期清理：回滚期间到期的工单留在表里。再次升级后读接口立即把它们当作不存在，进程启动时的第一轮清理就会删除（演练中日志为 `maintenance: ticket expiry changed 1 rows`）；
  - 其余工单（含未读标记、关联订单、整段对话）逐字节保留，升级回来后可以继续回复和关闭。
- 新前端对接旧后端：侧边栏没有“我的工单”，不发任何工单请求，直接访问 `/tickets` 显示“工单服务暂未开放”，管理后台“工单”页显示“当前版本暂不支持工单”，没有角标和圆点。旧前端对接新后端：旧前端不调用任何工单接口，行为不变。
- APP 不需要修改：工单只在网站上使用。四个平台的“复制诊断信息”只有应用版本、系统版本、连接状态和错误码，按钮说明是“联系客服时可粘贴这段信息”，与网站提交表单的提示一致。
- 演练证据：`scripts/test-release-rehearsal.py` 的“工单”阶段——在当前版本制造 8 张各状态的工单（待处理、已回复且未读并关联订单、客服带说明关闭、用户关闭、20 秒后到期、2 天后到期、一个即将注销账号的两张）→ 回滚到 75f906d：旧版本自己的注册流程新建账号并付款，有工单的账号注销后被旧版本清除（外键级联），新前端对接旧后端 → 再升级：到期工单立即 404 并被第一轮清理删除，其余行逐字节一致并可继续处理，旧版本注册的账号关联旧版本订单提交工单，新前端显示升级前的工单和角标；之后 `doctor` 在测试和开发配置下的两个警告；以及 75f906d 的旧网站对接当前后端。

## 七、安全审查结论（T3-04）

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 越权与 404 一致性 | 通过 | 用户接口每条查询都带“属于当前用户”的条件；别人的工单和不存在的工单返回逐字节相同的 404，非 UUID 参数直接 404（`TestTicketUserFieldWhitelist`）。用户接口不支持按工单号查询。普通用户和模拟会话访问 5 条管理员路由均为 403，管理员角色在事务内复核（`TestTicketConsoleQueueAndActions`）；未登录访问 6 条读接口和 6 条写接口均为 401（`TestTicketRequestBoundaries`） |
| 管理员身份不外泄 | 通过 | 用户接口的字段集合是白名单，与 `handoff_ticket.md` 第 10 节逐一相等，没有管理员 id、邮箱、`author_id`、`closed_by_admin`（`TestTicketUserFieldWhitelist`）；浏览器里用户侧只显示“客服”，页面文本不含“管理员”和管理员邮箱（`tickets.spec.ts` T2-01、T2-09） |
| XSS | 通过 | 标题、正文、回复里的 `<script>`、带 `onerror` / `onmouseover` 的标签、`javascript:` 链接和 `<iframe>` 原样存储；接口只返回 `application/json`，`<` `>` 转义为 `\u003c` `\u003e`，并带 `nosniff`（`TestTicketMarkupStaysText`）。前端以纯文本（pre-wrap）渲染，不用 `dangerouslySetInnerHTML`，不自动生成链接；浏览器里这些片段显示为文字，DOM 中没有对应元素，脚本不执行（`tickets.spec.ts` T2-09，`tickets.test.mjs` 源码检查） |
| CSRF | 通过 | 6 条工单写接口（提交、回复、关闭、已读、管理员回复、管理员关闭）：带 Cookie 但没有 Origin 返回 403 `origin_required`，不受信任的 Origin 返回 403 `origin_forbidden`，`text/plain` 和表单编码返回 415 `json_required`；被拒绝的请求没有改变任何数据（`TestTicketRequestBoundaries`） |
| 限流 | 通过 | 按用户的数据库限流（每天 5 张、每小时 30 条，跨实例有效）返回 429 并带 `Retry-After`，校验失败不消耗次数；每人最多 3 张未关闭、每张最多 100 条消息（`TestTicketIdempotencyAndCaps`、`TestTicketStateMachine`）；另有按 IP 的全局限流 |
| 请求体上限 | 通过 | Go：两个工单前缀恰好 32768 字节（3000 个汉字加空白填充）通过，32769 字节被拒（400，不写入）；前缀之外仍是 8 KB（`TestTicketRequestBoundaries`）。Next 代理：同样的 32 KB，`/me/ticketsx` 仍为 8 KB（`test:api-proxy`） |
| 日志与审计中无正文 | 通过 | `TestTicketTextStaysPrivate`（创建、回复、带说明关闭、到期）；演练里 5 个真实后端进程和 2 个 Next.js 进程的日志中没有标题、正文、回复、关闭说明、诊断信息、工单号、工单 id 或邮箱；审计 detail 只有长度和是否带说明 |
| doctor 无敏感输出 | 通过 | `TestTicketReadinessInBothConfigurations`（开发、生产、生产且关闭开关三种配置）与演练里测试、开发配置的真实 `doctor`：`tickets` 段只有开关、数量和时长，两个警告按条件出现，1 小时宽限内不报滞后，整份输出没有标题、正文、工单号、ID 或邮箱 |
| 枚举 | 通过 | 工单 id 是 UUID；工单号只用于显示和管理员搜索 |
| 已知并接受 | — | 工单正文可能包含用户自己写入的个人信息，它们存放在 `ticket_messages` 中直到 30 天到期，数据库备份里会有副本，备份的保留期由你的备份策略决定 |
