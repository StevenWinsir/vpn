# 支付、账号与管理后台：上线、实测、排查与回滚

对应交接书 `handoff_payment_account.md` 第 14 节第 6 轮与第 15、16 节。本文只写操作，设计理由见交接书；各项功能的细节见 `backend/DEPLOYMENT.md` 的对应小节。

## 结论边界（先读）

- 本仓库的所有支付验证都针对**按《支付接入技术文档》写成的本地模拟网关**。模拟网关只复现文档里写明的行为，不是真实网关。**真实网关的行为只有按下文“真实付款实测清单”付一次款才知道**，第一笔真实付款之前不要对外开放收款。
- 回调没有签名、签名不覆盖金额，因此自动开通完全依赖 `PAYMENT_NOTIFY_ALLOWED_IPS` 和金额下限。白名单为空时系统照常启动，但**所有回调都进入“待人工核对”，不会自动开通**，这是有意的安全默认。
- 本机无法验证的内容（真实网关、真实公网 HTTPS、真实邮件、真实 IP 归属地服务、四个平台 APP 的真机界面）不在 CI 内，需要你在部署后按清单确认。

## 一、发布顺序

1. 备份数据库，在新版本目录执行迁移（可重复执行，旧版本忽略新列和新表）：
   ```bash
   cd backend && ./api -migrate
   ```
2. 先保持 `PAYMENT_ENABLED=false` 上线新版本：网站没有可见变化，节点管理、APP、旧的测试购买照常。
3. 配置 Nginx 与 `TRUSTED_PROXIES`（下一节），再填写 `PAYMENT_CHANNEL`、`PAYMENT_SECRET`、`PAYMENT_NOTIFY_URL`（`https://<后端域名>/api/v1/payments/notify`）、`WEBSITE_BASE_URL`。开启 `PAYMENT_ENABLED=true`、`PAYMENT_TEST_PRICE_ENABLED=true`、`PAYMENT_TEST_PRICE=0.01`，`PAYMENT_TEST_PRICE_EMAILS` 只填你自己的测试账户，`PAYMENT_NOTIFY_ALLOWED_IPS` **先留空**，重启后端。
4. 运行只读诊断，确认没有意外：
   ```bash
   cd backend && ./doctor
   ```
   `payment` 段应显示 `enabled: true`、`auto_fulfil: false`、`test_price: true`，`warnings` 中有 `payment_callbacks_manual_review_only` 与 `payment_test_price_enabled`（此时是预期的）。
5. 按第三节完成 U-01 … U-09，在白名单里填入真实回调来源并重启。
6. 关闭测试价（`PAYMENT_TEST_PRICE_ENABLED=false`）并重启，再运行一次 `./doctor`：两条上述警告应当消失。观察 `payment_orders_need_review` 和 `rejected_callbacks_24h`。
7. 管理后台入口是 `/admin/console/…`（用户、订单、登录记录、优惠码、公告、套餐管理；套餐与年付的发布和回滚见第七节），与 `/admin/nodes` 是两套页面，不依赖节点目录开关。

## 二、Nginx、真实来源地址与回调路径

回调是网关服务器直接 `POST` 到 `PAYMENT_NOTIFY_URL`（`Content-Type: application/json`，不带 Cookie，不带 `Origin`）。网关每笔收款只回调一次，所以回调路径不套用浏览器的来源（`Origin`/Cookie）与 JSON 类型检查：无论带什么头、是 JSON 还是表单（`application/x-www-form-urlencoded`），都会先写入回调流水再判断，不会在记录之前被 403/415 拒掉。后端用 TCP 对端或受信任代理传来的 `X-Forwarded-For` 判断来源，所以必须保证后端看到的是**网关的真实地址**：

1. 后端域名的 `server` 块必须用 `proxy_set_header X-Forwarded-For $remote_addr;`（**覆盖**，不是追加）。不覆盖时，攻击者可以自填 `X-Forwarded-For` 冒充白名单地址。完整示例见 `docs/deployment.md`“真实来源地址”。
2. `backend/.env` 设置 `TRUSTED_PROXIES=127.0.0.1`（Nginx 与 Go 同机时），只有这些对端提供的转发头会被采用。未设置时 Go 看到的永远是 Nginx 的 `127.0.0.1`，回调来源会显示为本机，**白名单无法匹配**。
3. 回调地址使用后端域名，由 Nginx 直接转发给 Go，不要经过 Next.js 前端代理，也不要加登录、IP 限速或 WAF 验证码；回调路径对网关必须可达。后端自带每个来源地址每分钟 600 次的上限。
4. 3000、8080 只监听回环或受防火墙保护的私网，外部不能绕过 Nginx 直接访问，否则任何人都能自填来源头。
5. 配置后用 U-01 的结果验证：后台订单详情“回调流水”里的来源 IP 应该是网关公网地址，而不是 `127.0.0.1` 或你的 Nginx。若显示本机或内网地址，说明第 1、2 条没有生效。

## 四、排查指引

后台“订单与支付”→ 订单详情的**回调流水**是第一手资料。`处理结果`的含义：

| 结果 | 含义 |
| --- | --- |
| `accepted` | 回调已被接受：订单已开通，或收到“失败”回调后订单标为失败 |
| `duplicate` | 该订单已经付款，重复回调不再处理 |
| `ip_rejected` | 白名单非空，来源地址不在其中；订单未动 |
| `unknown_order` | `trade_no` 在本站没有对应订单 |
| `invalid` | 请求格式、金额格式或 `trade_status` 不合法（文档规定 `TRADE_SUCCESS` / `TRADE_FAILED`） |
| `review` | 进入待人工核对，原因见订单的核对原因 |
| `ignored` | 订单状态不允许再被回调改变（例如已被管理员关闭） |

核对原因：`unverified_source`（白名单为空）、`amount_mismatch`（实付少于应付，或高出超过 `PAYMENT_AMOUNT_TOLERANCE_CENTS`）、`state_conflict`（付款时套餐已不可开通，例如有效期内换了套餐）、`callback_missing`（网关说已付，但没有收到可信回调）、`gateway_unreachable`（长时间查不到网关状态）、`closed_by_admin`。

| 现象 | 可能原因与处理 |
| --- | --- |
| 下单后网关返回“签名验证失败” | 先核对 `PAYMENT_SECRET` 与商户号。**文档“签名示例”给出的值与文档文字描述的算法不一致**（算法 `MD5(trade_no + secret)` 得到的是 `becd5f2a…`），本站按算法实现；若网关确实按示例值验签，需要回报并单开修复 |
| 下单后网关返回“订单号已存在” | 同一 `trade_no` 重复提交；正常下单每次都是新号。若重复出现，检查是否有人手工复制了支付链接 |
| 付款后订单一直“待人工核对”，原因 `unverified_source` | 白名单为空或还没填。按 U-02 填入真实来源并重启；已付的订单用“人工确认到账” |
| 回调流水里来源是 `127.0.0.1` / 内网地址 | `TRUSTED_PROXIES` 或 Nginx 覆盖转发头没有配置，见第二节 |
| 回调流水里全是 `ip_rejected`，但来源看起来是网关 | 网关有多个出口地址；把该地址也加入白名单（逗号分隔，可写 CIDR），重启 |
| 回调流水为空 | 回调没到后端：核对 `PAYMENT_NOTIFY_URL`、Nginx、防火墙和证书；网关能否访问该地址 |
| 订单 `amount_mismatch` | 对照网关页面金额。同金额同支付方式有未超时订单时，网关会逐笔加 0.01，容差默认 0.50 元；确认实收后“人工确认到账”并填写实收金额 |
| 结果页一直显示“支付已完成，正在确认到账”，订单记录显示“已付款，确认中” | 网关状态接口已报告付款，但可信回调还没把订单开通（没到、被拒或在核对）；这只是提示，不会开通。看回调流水；本地窗口（默认 180 秒）过后对账循环会把订单变成待核对（`callback_missing`），后台订单详情的“网关报告已付”是网关第一次报告付款的时间 |
| 付款成功但订单显示“已超时” | 晚到的成功回调仍会开通（已付款优先）。若没有，查看回调流水；已被管理员关闭的订单不会再被回调改变 |
| 用户说“优惠码无效” | 不存在、已停用、未到期或已过期、已删除，界面统一提示“无效或已失效”；不适用于所选套餐、已用完、本人已用过会有各自提示。每个账号每小时最多 20 次无效尝试 |
| 用户删除账号被拒绝，提示还有未完成订单 | 订单需要等到失效（最多 `PAYMENT_PENDING_LIMIT_SECONDS`）再删 |
| `./doctor` 报 `account_purge_stuck` | 有账号处于 `deleting` 超过 1 小时：看后端日志 `account purge has failed`（只含用户 UUID），通常是节点还没确认释放；超过 `NODE_AGENT_SETTLE_GRACE_SECONDS` 后会自动清除 |
| 管理员模拟登录后看不到公告、无法操作 | 这是设计：模拟会话只读、不显示公告、不写登录记录，到点（`IMPERSONATION_MINUTES`）自动结束 |

后端日志不输出密钥、签名、完整 `trade_no`、网关 URL、密码或令牌；回调相关行形如 `payment notify <id>: review (trade …a1b2c3)`；`ip_rejected`、`invalid`、`unknown_order` 的行另带来源地址（`… ip_rejected from 203.0.113.10 (trade …a1b2c3)`），用于核对 `PAYMENT_NOTIFY_ALLOWED_IPS`。

## 五、回滚

1. `PAYMENT_ENABLED=false` 并重启，停止新下单。确认没有活动中的待付订单（`./doctor` 的 `payment.pending_orders` 为 0；待付订单最多存活 `PAYMENT_PENDING_LIMIT_SECONDS`）。
2. **撤销全部模拟登录会话**（旧版本不认识“只读”规则，会把它们当成可写的普通登录）：
   ```bash
   cd backend && ./api -revoke-impersonation
   ./doctor    # impersonation.active_sessions 应为 0
   ```
   每个被撤销的会话在审计里留一条 `admin.impersonate_revoked`。命令可重复执行。
3. 换回上一版本的二进制并重启。**不需要也没有反向迁移**：新列可空或有默认值，新表被旧版本忽略。处于 `deleting` 的账号在旧版本同样无法登录，数据等回到新版本后由清除循环删除。
4. 回滚期间到达的网关回调没有处理程序（404）。回到新版本后，对账循环或人工核对会处理这些订单；晚到的成功回调仍然开通。
5. 已有演练证据见 `scripts/test-release-rehearsal.py`（备份 → 迁移 → 全流程 → 三次回滚（含套餐商店之前的版本）→ 再升级），它在私有数据库上运行，不触碰任何线上环境。

## 六、安全审查结论（R6-03）

逐项检查及证据（均为可重复执行的测试）：

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 回调只认白名单来源；伪造转发头无效 | 通过 | `TestSecurityPaymentBypassAttempts`（`X-Forwarded-For` / `X-Real-IP` / `Forwarded` 等头；白名单外地址 → `ip_rejected`） |
| 金额下限 | 通过 | 同上：少付、超过容差、畸形金额均不开通 |
| `trade_no` 不可预测 | 通过 | 8 位日期加 12 位 `crypto/rand`；2000 个样本无重复，相邻号码为未知订单 |
| 浏览器不能指定金额 | 通过 | 订单和报价请求中的任何金额、状态、用户、回调地址字段都被拒绝（`invalid_json`）；价格只在服务端由套餐、测试价名单和优惠码算出 |
| 模拟会话只读 | 通过 | `TestSecurityRouteAccessMatrix` 遍历整张路由表：所有写路由返回 `impersonation_read_only`；`TestImpersonation*` |
| 二次验证 | 通过 | 高风险管理操作要求管理员再次输入密码，错误次数按管理员计数（5 次 / 15 分钟）；见 `TestConsole*` |
| 日志脱敏 | 通过 | `TestSecurityLogsStayClean`、`TestUserPaymentChecklist` U-09：无密钥、签名、网关 URL、完整订单号、密码 |
| XSS | 通过 | 公告与名称按纯文本渲染；接口一律 JSON，带 `nosniff`、`X-Frame-Options: DENY`、`Cache-Control: no-store`；全仓库无 `dangerouslySetInnerHTML`；浏览器用例验证 `<script>` 不执行 |
| 越权访问（IDOR） | 通过 | `TestSecurityObjectAccess`：他人订单 404、列表只含本人、登录记录按用户隔离、公告确认不能指向不存在的公告；路由表测试：所有 `/admin/*` 对普通用户拒绝，所有非公开路由对匿名用户 401（新增路由若漏写鉴权会使测试失败） |
| 优惠码枚举限流 | 通过 | 每账号每小时 20 次无效尝试后返回 429（`TestPaymentCoupons`）；不存在、已停用、已过期、已删除的返回完全相同 |
| 生产配置拒绝模拟购买 | 通过 | 配置加载拒绝 `TEST_PURCHASE_ENABLED=true`（`TestPaymentProductionRules`）；即使该标志被带入生产，处理函数也返回 403（`TestProductionConfigurationDefenses`） |

已知且接受的剩余风险：

- 回调没有签名：在白名单之外的伪造请求不能开通订单，但白名单为空时（只在首次学习来源阶段）任何知道订单号的人都能把订单推进到“待人工核对”，不会自动开通；订单号只有订单所有者和网关知道。
- 优惠码的“不适用 / 已用完 / 已用过”提示会说明该码存在，受每账号每小时 20 次限制，注册需要邮箱验证。
- 回调接口按来源地址限速，且每次回调都会写一行 `payment_notifications`（保留 180 天）。如果后端直接暴露在公网，可在 Nginx 对该路径另加限速；同机部署 + 第二节配置下，外部流量无法绕过 Nginx。
- `requireAuth` 对每个请求多一次会话关联子查询（主键索引，开销可忽略）。

## 七、套餐商店与年付：发布、回滚与实测（handoff_shop.md 第 4 轮）

套餐由管理员在 `/admin/console/plans`（“套餐管理”）定义；每个套餐可开启年付，年付价 = 月价 × 12 × 折扣 ÷ 100（向下取整到分），默认 9 折，全局折扣和单个套餐的折扣都可以调整。年付与月付是同一个套餐的两个付费周期，购买年付时订阅的套餐 ID 不变，因此 APP 保持在线。年付的流量不是一次性发放：从付款时刻起每 30 天，本周期额度重置为套餐的月流量（未用完不累计，用完则等下次刷新）；月付续成年付时，剩余的月付流量并入第一个 30 天周期；已是年付时再续费（年付或月付）只顺延有效期，刷新日期不变。套餐只做软删除，不会因为迁移或旧版本启动而复活。

### 7.1 发布顺序

1. 备份数据库，部署**后端**并执行迁移（只增不删，可重复执行）：`cd backend && ./api -migrate`。此时 `/plans` 已带有年付数据，但旧前端不显示，对用户无可见变化。
2. 运行 `./doctor`，看 `shop` 段：`settings_row_present: true`，`yearly_discount_percent: 90`，`active_plans` 与 `active_yearly_plans` 符合预期。`plans_over_device_cap` 只是数量，不是警告（见下一条）。
3. 在“套餐管理”确认三个种子套餐的年付参数和全局折扣；**套餐的设备额度不能超过 `CLIENT_MAX_ONLINE_DEVICES`**（默认 2，生效上限 = min(套餐设备数, 该值)）。要让进阶、旗舰的 5 / 10 台生效，调高该变量并重启后端；套餐列表同时显示设定值与生效值，超过时有警告图标。
4. 再部署**前端**，年付正式对外。顺序必须是先后端、后前端。
5. 按 7.3 用测试价做一次真实年付付款。

### 7.2 回滚

- 只想撤下年付，不需要回滚代码：在“套餐管理”逐个关闭年付，页面会自动隐藏切换控件和横幅。
- 回滚代码前：
  1. **停用所有有周期范围（仅月付 / 仅年付）的优惠码**。旧版本不认识周期范围，会把它们当作全部周期适用；

## 九、推荐码与推荐送流量：发布、排查、回滚与实测（handoff_coupon.md 第 3 轮）

每位用户有一个 8 位推荐码（数字 2–9 加上除 I、L、O 外的大写字母，用户第一次打开 `/referral` 或总览摘要卡时生成，不改变）。新用户在 `/register` 填写推荐码（或打开邀请链接 `/register?ref=推荐码`）注册，推荐关系在注册事务里绑定；被推荐人第一次真实付款（网关回调或管理员确认到账；测试购买不算）后，推荐人在**发放时**有有效套餐的前提下，获得与该订单实付金额等额的流量（1 元 = 1 GiB），加在推荐人当前订阅上。无效的推荐码不报错，注册照常成功，只是不绑定。奖励只认首单；发放时推荐人没有有效套餐，这笔奖励作废，不会补发；年付订阅的奖励不会被 30 天刷新清零，订阅期结束后作废。

### 9.1 发布顺序

1. 备份数据库，部署**后端**并迁移（只增不删，可重复执行）：`cd backend && ./api -migrate`。迁移会在 `users` 上建 `referral_code` 唯一索引，写入会短暂阻塞，请在低峰期执行；已有用户不回填。
2. 运行 `./doctor`，看 `referral` 段：`enabled: true`，各状态计数为 0，`stale_qualified` 为 0；确认 `curl /api/v1/meta` 里出现 `"referral_enabled": true`。
3. **再部署前端**。顺序必须是先后端、后前端：新前端只在 `/meta` 里有 `referral_enabled` 为真时才显示推荐码字段并发送 `referral_code`；旧后端的请求解码拒绝未知字段，收到该字段会让注册失败。
4. 按 9.4 用测试价做一次真实推荐实测。
5. 三个环境变量（都有默认值）：`REFERRAL_ENABLED`（默认 `true`）、`REFERRAL_REWARD_MAX_GIB`（单笔封顶，0–10240，0 表示不封顶）、`REFERRAL_POLL_INTERVAL`（发奖轮询间隔，1s–5m，默认 10s）。关闭开关时：注册忽略推荐码、页面入口隐藏、发奖暂停，但被推荐人的首单仍照常记为“待发放”，重新开启后按当时的条件补发。

### 9.2 排查指引

先看后台“用户管理”里该用户详情的“推荐”分区：推荐码、推荐人、统计和每条被推荐记录的状态（完整邮箱只在这里可见），再对照下表。`./doctor` 的 `referral` 段只给开关、封顶和各状态数量，不含邮箱、推荐码或 ID。

| 现象 | 原因与处理 |
| --- | --- |
| 被推荐人付款后，推荐人迟迟没有奖励，记录是“待发放” | 发奖循环每 `REFERRAL_POLL_INTERVAL` 秒运行一次，正常在付款后约 10 秒内完成。超过 10 分钟 `./doctor` 会警告 `referral_rewards_stale`：看是不是 `REFERRAL_ENABLED=false`（开关关闭时发奖暂停），或 API 进程没有运行；数据库临时错误会按 30 秒、1 分钟……最长 30 分钟退避重试，详情页里有“重试中”的错误类别（只有类别，没有个人信息） |
| 记录是“未生效（发放时无有效套餐）” | 发放时推荐人没有有效期内的订阅（过期、从未购买，或生产环境下只有测试订阅）。这是终态，之后推荐人再买套餐也不补发；需要补偿请在“用户管理”里手动改推荐人的订阅流量 |
| 记录是“未生效（账号不可用）” | 发放时推荐人正在注销或已停用 |
| 被推荐人说自己填了码，推荐人看不到记录 | 码写错、推荐人当时正在注销或已停用、开关当时关闭，或用户是从 APP 打开的注册页（不带 `?ref`）后没有手填。无效码不报错是设计如此；绑定只发生在注册那一刻，不能补填 |
| 被推荐人的第二笔订单没有奖励 | 只认第一笔真实付款，设计如此 |
| 记录一直是“已注册·未消费”，但被推荐人已付过款 | 付款发生在旧版本（回滚期间）或绕过了履约入口。每 10 分钟的补扫会处理；也可以重启后端立即触发一次 |
| 年付推荐人的奖励在 30 天刷新后变少 | 刷新时保留的奖励 = 未用完的奖励（先用周期额度，最后用奖励），用掉的部分不保留；订阅期结束（过期后重新购买）奖励作废 |

### 9.3 回滚

- 只想撤下推荐功能，不需要回滚代码：`REFERRAL_ENABLED=false` 并重启后端。前端入口和注册字段随 `/meta` 自动隐藏。
- 回滚代码：**先回滚前端，再回滚后端**，不需要手动处理数据（新增的列和表保留在数据库里）。回滚到 PR #77（8c311ee）时：
  - 旧版本忽略新表和新列，外键保证旧版本的删号清除不会失败（删除被推荐人保留记录并把被推荐人置空，删除推荐人带走他的全部记录）；
  - 回滚期间被推荐人完成的首单不会被判定，升级回来后由每 10 分钟的补扫处理（首单仍是最早一笔真实付款）；
  - 回滚期间推荐人如果在奖励所属的订阅期结束后重新购买，奖励的锚点失效，这部分奖励不会带进新的订阅期（总览和推荐页都显示 0）；
  - 旧版本的年付刷新不认识奖励，会在刷新点把当期奖励刷掉；升级回来后下一次刷新可能按“未用完的部分”恢复一部分奖励。回滚窗口很短，这个结果对用户有利，接受它。
- 新前端对接旧后端：注册页没有推荐码字段，请求体与旧版本完全一致，侧边栏入口和总览摘要卡隐藏，直接访问 `/referral` 显示“功能暂不可用”且不发请求（`referral.spec.ts` R2-05、`referral-compat.spec.ts`）。旧前端对接新后端：请求没有新字段，行为不变（演练的旧网站阶段）。
- APP 不需要修改：奖励体现在订阅的 `traffic_limit_bytes` 上，会话指纹不变，在线期间收到奖励不会被要求重新授权，APP 在下一次刷新额度时显示新的总量。
- 演练证据：`scripts/test-release-rehearsal.py` 的“推荐”阶段——通过真实注册流程绑定 6 条推荐关系 → 真实付款与真实发奖进程产生已发放 / 未生效 / 关闭开关期间的待发放记录，年付推荐人带着奖励 → 回滚到 PR #77 → 旧版本完成一笔首单、推荐人换新订阅期、删号 → 再升级：补扫判定首单并发奖、锚点失效的奖励不再可见、年付刷新保留奖励、`doctor` 的计数与滞留警告；以及 PR #78 的旧网站对接当前后端。

## 十一、套餐有效期内升级（补差价）：规则、后台、排查、回滚与实测（handoff_plans.md 第 3 轮）

订阅有效期内，用户可以在 `/plans` 把当前套餐**升级**到更高的套餐：到期日不变，只为剩余天数补差价。**降级不支持、不退款**：页面和接口都提示“当前套餐有效期内不支持降级（降级不退还差价），请在 {到期日} 到期后购买”。价格由服务端计算，所有取整都向商家有利的方向取，抵扣只按用户在本周期**实际付过的钱**和**剩余时间**计算。

### 11.1 规则

每张套餐卡相对于当前订阅的关系（前提：订阅存在、不是测试订阅、`starts_at ≤ 现在 < expires_at`；否则所有套餐都按“新购”处理）：

| 关系 | 条件 | 页面与接口 |
| --- | --- | --- |
| 当前（current） | 就是当前套餐 | 续费，规则不变 |
| 升级（upgrade） | 目标套餐上架可买，**月付价格严格更高**，日流量不低于当前、设备数不少于当前、当前有专线时目标也有专线 | 按钮“升级到 {B}”，小字“补差价约 ¥X，到期日不变”；剩余不足 24 小时、或后台关闭了升级开关时按钮禁用并写明原因 |
| 降级（downgrade） | 目标的月付价格更低 | 按钮禁用，“到期后可购买”，提示含到期日；**不退差价** |
| 不可更换（lateral） | 价格相同，或价格更高但流量、设备或专线某项更低 | 按钮禁用，提示“{B} 与当前套餐权益不可直接升级，请在 {到期日} 到期后购买” |

其他约定：升级不能使用优惠码；升级不改变付费周期（月付持有按月付条款补差价，年付持有按年付条款补差价；想改成年付，升级后再续费为年付）；有一笔未完成的升级订单时不能再下任何订单，有任何未完成订单时也不能下升级订单（`409 pending_order_exists`，约 3 分钟后订单超时即可再试）；测试价名单内的账户，升级应付额同样换成测试价。

### 11.2 算法与算例

记 R = 到期时间 − 现在。

1. **天数**：收费天数 Nc = R 按 24 小时**向上**取整，抵扣天数 Nk = R 按 24 小时**向下**取整；要求 Nk ≥ 1（剩余至少 24 小时）。
2. **新套餐剩余价值 V** = 新套餐日单价 × Nc，**向上**取整到分（月付持有按月付价格和天数；年付持有按年付价格和 365 天，目标套餐没有年付时按月付价，日单价更高）。
3. **已付残值抵扣 K**：本周期内每笔已付订单（不含测试购买）的金额（取应付与实付的较小值）按时间均匀分布在它的“价值覆盖区间”上，取区间落在最后 Nk 整天里的部分，**向下**取整，求和。新版本写下的订单记录了覆盖区间（开新周期为 [付款时刻, 到期]，续费为 [原到期, 新到期]，升级为 [付款时刻, 到期]）；旧版本写下的订单没有记录，按 [付款时刻, 付款时刻 + 天数] 兜底，这个兜底区间的开始时间不会晚于真实区间，所以只会少抵、不会多抵。管理员赠送或延长的天数没有订单覆盖，不产生抵扣。
4. **应付** = max(V − K, 最低补差)，最低补差默认 1.00 元（后台可改，0.01–100.00 元）。
5. **新增流量** = (新套餐日流量 − 当前套餐日流量) × Nc，新套餐部分向下取整、当前部分向上取整，不小于 0；用户剩余的流量原样保留。年付持有时：本 30 天周期按“到下次刷新的剩余天数”补差额，之后每次刷新的额度变成新套餐的月流量。
6. **履约**：只改订阅的套餐、设备数、专线权限和流量；`starts_at`、`expires_at`、已用流量、推荐奖励、刷新锚点都不变，计量账本仍是同一周期。

种子套餐的算例（轻量 19.90 / 30 天 / 100 GiB；进阶 39.90 / 300 GiB；旗舰 79.90 / 800 GiB；年付 9 折）：

| 场景 | 结果 |
| --- | --- |
| 11-01 00:00 月付买轻量（19.90），11-11 10:00 升级到进阶（R = 19 天 14 小时，Nc 20，Nk 19） | V = 26.60，K = 12.60，补 **14.00 元**，新增约 133.33 GiB，到期日仍是 12-01 |
| 接着 11-21 10:00 升级到旗舰（Nc 10，Nk 9） | V = 26.64，K = 5.97 + 6.43 = 12.40，补 **14.24 元**；三笔共 48.14 元，按精确天数算的公平价值是 45.73 元 |
| 年付轻量（214.92，2026-01-10 购买）在 2026-11-02 12:00 升级到进阶（Nc 69，Nk 68） | V = 81.47，K = 40.03，补 **41.44 元**；本周期补约 26.67 GiB，之后每 30 天 300 GiB |
| 用了 5 折优惠码的轻量（实付 9.95），时间同第一例 | K = 6.30，补 **20.30 元**（优惠只作用于已经用掉的部分） |
| 续费叠加后升级（到期 12-31，11-26 00:00 升级，Nc = Nk = 35） | V = 46.55，K = 23.21，补 **23.34 元**；若续费单是旧版本写下的（兜底区间），K = 22.54，补 24.01 元，用户多付 0.67 元，商家不会少收 |
| 进阶降级到轻量 / 剩余 20 小时 | 拒绝，分别提示到期后购买 / “剩余不足 1 天，请到期后直接购买新套餐” |

### 11.3 后台

- **套餐管理 → 有效期内升级**：“允许有效期内升级”开关（默认开启）和“最低补差金额（元）”（默认 1.00，0.01–100.00）。保存走乐观锁并写审计（记录前后值）。关闭开关后，`/plans` 的升级按钮禁用；已经打开的升级弹窗点支付会得到“暂未开放有效期内升级”的提示，不会下单。
- **订单与支付**：订单列表有“类型”列（“升级 / 从 A”）和“订单类型”筛选；升级订单的详情多一张“升级明细”卡：订阅 ID、周期（升级不改变）、持有方式、Nc / Nk、V 与费率、K、是否按最低补差、新旧流量费率、新增流量、之后每周期额度、升级后不可再用的线路组，以及抵扣来源（计入的订单和各自金额）。“价值覆盖”一行是该订单的覆盖区间。
- **订阅编辑**（用户管理）不变：管理员仍可以直接改用户的套餐，这不是“按差价升级”，不产生订单。

### 11.4 发布顺序

1. 备份数据库，部署**后端**并迁移（只增不删，可重复执行）：`orders` 增加 `kind`、`from_plan_id`、`from_plan_name`、`credit_cents`、`upgrade_days`、`upgrade_traffic_bytes`、`upgrade_snapshot`、`covers_from`、`covers_to`；`shop_settings` 增加 `upgrade_enabled`、`upgrade_min_charge_cents`。没有新表，不需要环境变量（升级的总前提是 `PAYMENT_ENABLED=true`）。
2. 运行 `./doctor`，看 `shop` 段：`upgrade_enabled`、`upgrade_min_charge_cents` 是预期值，`upgrade_review_orders` 为 0；`upgrade_group_gaps` 列出的线路组缺口按 11.6 处理。确认 `curl /api/v1/meta` 出现 `"plan_upgrade_supported": true`。
3. **再部署前端**。新前端只在 `/meta` 的 `plan_upgrade_supported` 为真时才请求升级接口；后端较旧时退回原来的本地判定，文案为“当前套餐有效期内不能更换，到期后可购买”，不出现“升级”。
4. **APP 不需要发布**：升级改变了订阅的权益指纹，已登录的客户端在下一次与服务端交互时（节点目录轮询约 5 秒、上报或心跳）断开，提示“套餐已变更，请重新登录”，重新登录后按新套餐取线路和授权。
5. 按 11.9 用测试价做一次真实升级实测。

### 11.5 人工审核的升级订单

升级订单只会按下单时的订阅开通。付款到达时（回调或管理员确认）如果订阅已经不是下单时的那一个——管理员改了到期时间或套餐、订阅已过期、另一笔续费抢先开通，或者回调落在了回滚后的旧版本上——订单转为“待核对”（`state_conflict`），**不会自动改成别的东西**。处理办法：

| 情况 | 处理 |
| --- | --- |
| 订阅其实没变（例如回滚期间回调落在旧版本上，升级回来后） | 在订单详情点“确认到账”，填写网关后台核实的实付金额和备注，即按下单时的计算开通；`./doctor` 的 `upgrade_orders_need_review` 随之消失 |
| 订阅确实变了，确认到账返回“当前订阅状态不允许开通此订单”（`fulfil_conflict`） | 二选一：①在网关商户后台给用户退款，然后在订单详情“关闭订单”；②按用户实际付的钱在“用户管理”里手动调整订阅（例如改成目标套餐），再关闭这笔订单。不要为它再开一笔升级订单 |
| 实付金额与订单不符（`amount_mismatch`） | 与普通订单相同，见第四节 |

### 11.6 doctor 警告

| 警告 | 含义与处理 |
| --- | --- |
| `upgrade_orders_need_review` | 有处于“待核对”的升级订单（数量在 `shop.upgrade_review_orders`），按 11.5 处理 |
| `plans_upgrade_group_gap` | 存在“A 能升级到 B，但某个启用的线路组 A 能用、B 不能用”的组合，`shop.upgrade_group_gaps` 逐条列出 “A>B:组名”。升级弹窗会用红色警告列出这些线路，用户仍可升级；如果不希望出现这种情况，在线路组的“可用套餐”里把 B 也勾上 |
| `shop_upgrade_settings_invalid` | 设置行里的最低补差超出 0.01–100.00 元，在后台重新保存一次 |

### 11.7 回滚

- 只想暂停升级，不需要回滚代码：后台关闭“允许有效期内升级”。
- 回滚代码：可以直接回滚二进制，新列留在库里无害。回滚前先用 `./doctor` 看 `upgrade_review_orders`，并处理掉未完成的升级订单（或接受它们在回滚期间转为待核对）。回滚到 PR #99（dbe75ca）时：
  - 旧版本读到升级订单时，它卖的是 0 天、0 流量，旧的履约一定判定失败：回调转为“待核对”（`state_conflict`），管理员确认到账得到 `fulfil_conflict`，**永远不会被当成普通订单开通**；升级回来后订阅没变的，可以按 11.5 确认到账；
  - 旧版本照常卖套餐和续费，这些订单没有覆盖区间、类型默认为普通购买，升级回来后按兜底区间计算抵扣（只会少抵）；
  - 旧版本的控制台把升级订单显示成“{B} / 0 天”，旧网站的订单记录同样如此，只影响显示；
  - 回滚期间仍未付款的升级订单，升级回来后迟到的回调照常开通（订阅没变时）。
- 新前端对接旧后端：`/meta` 里没有 `plan_upgrade_supported`，页面不请求升级接口，其他套餐显示“到期后可购买”。旧前端对接新后端：其他套餐仍显示“当前套餐有效期内不能更换套餐，到期后可购买。”；如果直接调用普通下单，后端返回 `409 plan_change_not_supported`，提示按方向区分（升级提示可以“升级”补差价，降级提示不退差价和到期日）。
- 演练证据：`scripts/test-release-rehearsal.py` 的“套餐升级”阶段——当前版本上三个账户买轻量、一笔升级付款、两笔升级待付款 → 回滚到 dbe75ca：回调和人工确认都只转人工，旧版本照常续费和新购 → 再升级：迟到回调开通、待核对订单人工确认开通、旧版本订单按兜底区间抵扣，报价与脚本按数据库行独立计算的结果逐分相等；以及 dbe75ca 的网站对接当前后端、当前网站对接 dbe75ca 和再升级后的后端（`plans-compat.spec.ts`）。

### 11.8 APP 与客户端

- 升级功能本身不需要改 APP。四个平台都通过同一个 Core：收到 `subscription_changed` 后停掉隧道、清掉会话，界面显示“套餐已变更，请重新登录”；保存了密码的客户端也**不会**静默重新登录，需要用户自己登录一次，登录后按新套餐授权（专线、设备数）。
- 计量：节点计量（生产环境）下，升级前已发出的节点授权在同一周期内继续有效到空闲超时，这段时间内节点上报的用量照常扣到升级后的余额上（`TestUpgradeLateNodeUsageStaysInPeriod`）。客户端计量（仅开发 / 测试环境，生产环境拒绝客户端上报）下，已经发出的上报照常扣费；Core 因 `subscription_changed` 结束会话时，先关闭数据通道，再用仍然有效的令牌把上一次上报之后的尾量作为最后一次上报结算（同一订阅、同一周期，按连接绑定的倍率），尾量确认后释放在线租约，最后才清掉会话。管理员在后台改套餐时同样如此。如果服务端已经换了周期（`nativeBound` 不成立），最后一次上报会被 409 拒绝，尾量不计入新周期，租约随之自然过期。令牌失效的原因（`native_session_*` 等）不发送任何请求，只关闭数据通道。这一修复改动了四个 APP 共用的 Core，需要随下一次 APP 发版生效；在此之前的旧版 APP 仍会丢掉最多一个上报间隔的尾量。
- 自动化证据：`TestCoreUpgradeDisconnect`（真实 Core 进程 + 真实支付流程；升级前刚上报完就再带上 1 + 2 MiB，断开后这部分按 0.5 倍扣到同一周期，在线租约以 released 结束）、Core 单元测试 `TestSubscriptionChangedSettlesTheTail`、`TestDeadTokenDropsTheTailUnsent`、`TestShutdownWaitsForTheDroppedTail`、Core 线束 `A04-upgrade`（宿主 macOS 与 iOS 模拟器进程里的真实 Core + 真实 Mihomo 引擎；升级前下载的 1 MiB 必须全部按线路倍率计费）、Android `BillingAcceptanceTest` 的 `A04-upgrade`（模拟器里的真实 APP）、macOS `testPlanUpgradeWhileConnectedSignsOutWithTheCoresWords`、Windows `Core_ending_the_session_without_a_saved_password_just_asks_to_sign_in`。真机表现由 U-42 确认。

## 十二、套餐升级的安全审查结论（R3-04）

先逐条复核规划第 6.8 节“商家不吃亏”的论证，再查实现上的攻击面。

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 抵扣不超过真实残值 | 通过 | K 只取覆盖区间落在剩余整天里的部分并向下取整；旧订单的兜底区间开始得更早，只会少抵；赠送和延长的天数没有订单覆盖。`TestUpgradeInvariantTrajectories`（2000 条随机轨迹，独立的精确有理数模型）逐次验证 K ≤ 真实残值；演练里旧版本续费单的兜底抵扣小于其真实区间的抵扣 |
| 剩余时间按新套餐全价收 | 通过 | 应付 + 真实残值 ≥ 新套餐在剩余时间内的标价（同一随机测试逐次验证）；收费天数向上取整，V 向上取整 |
| 已消耗的不折现 | 通过 | K 只看时间，不看剩余流量；新增流量在 0 与 (B − A) 日流量 × Nc 之间（随机测试逐次验证） |
| 没有负价、退款或叠加优惠 | 通过 | 最低补差兜底；升级下单拒绝 `coupon_code` 等一切未知字段；有效期内带优惠码走普通下单买更高套餐同样被拒（`TestUpgradeSecurityMoney`）；降级和不可更换都没有接口 |
| 连续升级不重复收费 | 通过 | 后一次的抵扣包括前一次升级单的残值（算例二，`TestUpgradeExamplesMonthly`；演练里续费后再升级到旗舰） |
| 金额篡改 | 通过 | 请求不带金额；`amount_cents`、`price_cents`、`credit_cents`、`upgrade_days`、`billing_cycle`、`user_id` 等字段一律 400；`expected_amount_cents` 只能让服务端拒绝（偏低、偏高 409 `price_changed`，缺失、0、负数 400），被拒的请求不产生订单（`TestUpgradeSecurityMoney`） |
| 报价与下单之间改价 | 通过 | 下单在用户行锁内重新计价，与 `expected_amount_cents` 不一致即 409，重新报价得到新价（`TestUpgradeSecurityMoney`）；网站在这种情况下显示“价格已更新”且不打开网关（R2-04） |
| 下单与付款之间改价 | 通过 | 订单按下单时的快照付款与开通：付的是订单金额，设备数和新增流量取快照，管理员之后改套餐价格、流量或设备数都不影响这笔订单（`TestUpgradeSecurityMoney`） |
| 回调伪造与重放 | 通过 | 非网关地址的回调被拒绝记录（`ip_rejected`），订单仍待付款；少付的回调转待核对（`amount_mismatch`）；重复回调只开通一次（`TestUpgradeSecurityCallbacks`） |
| 对别人订单的重放 | 通过 | 幂等键按用户隔离，别人用同一个键只会得到自己的订单；别人的订单详情与不存在的订单响应逐字节相同（404），也不出现在列表里（`TestUpgradeSecurityOwnership`） |
| 模拟登录下单 | 通过 | 模拟会话读 `upgrade-options` 可以，`upgrade-quote` 和 `upgrade-orders` 都是 403 `impersonation_read_only`（`TestImpersonationIsReadOnly`） |
| 跨站请求与未登录 | 通过 | 升级写接口缺少或伪造 Origin 403、非 JSON 415、未登录 401；停用账号不能下升级单（`TestUpgradeSecurityOwnership`） |
| 信息泄露 | 通过 | 用户接口只多出 5 个字段，计算快照、覆盖区间、订阅 ID、来源套餐 ID、幂等键都不对用户输出（`TestUpgradeSecurityOwnership`、`TestUpgradeKeepsPeriodAndChangesFingerprint`）；演练里三个真实后端进程的日志不含邮箱、密码和支付链接 |
